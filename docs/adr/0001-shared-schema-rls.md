# ADR-0001 — Shared schema with row-level security for multi-tenancy

**Status:** ACCEPTED · **Date:** 2026-11-24 · **Supersedes:** none
**Implementation:** `src/db/schema/rls.ts`, `src/db/tenant.ts` — tested by
`tests/integration/isolation.test.ts` (Phase 1a, 2026-11-24).

## Context

VANNY MANAGER PRO serves many unrelated businesses. A leak between tenants is the single
most damaging failure mode available to this product — it destroys the trust of every
customer at once, not just one. Three isolation models were considered:

| Model | Verdict |
|---|---|
| Database per tenant | Rejected — operational overhead, no benefit at this scale, hostile to serverless pooling |
| Schema per tenant | Rejected — migration fan-out, no cross-tenant analytics, painful to evolve |
| Shared schema + `org_id` + RLS | **Accepted** |

## Decision

One database, one schema. Every tenant table carries `org_id uuid NOT NULL`. Isolation is
enforced at **three** independent layers, because any single layer will eventually be
bypassed by a bug:

1. **Type system.** `withTenantDb(orgId, fn)` in `src/db/tenant.ts` is the only sanctioned
   way feature code reaches tenant tables. It validates the org id, wraps the work in one
   transaction, and applies `SET LOCAL` (via `set_config(..., false)`) before `fn` runs.
   `client.ts` (`getDb()`) is reserved for platform-level / migration work and is not a
   path to tenant data. Feature code cannot express an unscoped tenant query.
2. **Row-Level Security.** One shared policy per table, generated by
   `tenantIsolationPolicy(column)` in `src/db/schema/rls.ts`:
   `USING (col = current_setting('app.org_id', true)::uuid)` and the same `WITH CHECK`.
   `SET LOCAL` inside a transaction — safe on PgBouncer/Neon pooling.
   `current_setting(..., true)` returns `NULL` when unset, and `NULL = x` filters
   everything → **fail-closed**.
3. **Automated tests against a real PostgreSQL.** Org A vs Org B across read and write
   paths, plus a direct-SQL unscoped test and an owner-role control test. Merge blocker.

The runtime role does **not** hold `BYPASSRLS` and is not the table owner. The migration
role does.

## Findings from the real-DB test run (2026-11-24)

These only became visible once the schema was applied to an actual PostgreSQL server:

- **RLS policy violations report SQLSTATE `42501`** (insufficient_privilege), not `23514`.
  Tests assert on `42501`.
- **drizzle-kit emits FK statements before index statements.** The composite FK
  `product_prices(product_id, org_id) → products(id, org_id)` therefore must be backed by a
  UNIQUE *constraint* (inlined in `CREATE TABLE`), not a unique index, or the generated
  migration fails on a fresh database. Fixed in `src/db/schema/catalog.ts`.
- **PostgreSQL checks PK before FK.** A price row for a foreign tenant whose
  `(product_id, currency)` pair already exists fails the PK, not the FK — the isolation
  tests choose data that isolates the specific constraint under test.

## Consequences

- **+** Cheap, pooled-connection friendly, one migration path, cross-tenant reporting
  possible for the platform admin surface.
- **+** A missed `org_id` filter returns an empty set, not another tenant's rows
  (proven: unscoped app connection sees 0 rows).
- **−** Every new tenant table needs its `org_id` column, its index, and its RLS policy.
  **Outstanding:** a CI catalog-introspection test (`pg_policies`) that fails if a table
  with `org_id` lacks an enabled policy — scheduled with the Phase 1b migration tests.
- **−** Platform admins need an explicit, audited path rather than a role flag.
- **−** `SET LOCAL` discipline is mandatory; a session-level `SET` on the pooled connection
  would leak the tenant. Code review rule: only `SET LOCAL`, only inside a transaction —
  `withTenantDb` is the only code that touches the setting.

## Verification

- `tests/integration/isolation.test.ts` — 11 tests, real PostgreSQL via
  `tests/integration/pg-harness.ts` (embedded-postgres, port 55433, trust auth,
  localhost only). Covers: read isolation (including known-id), fail-closed unscoped
  access, owner control, cross-tenant INSERT (42501), cross-tenant UPDATE (0 rows),
  composite FK tenant integrity (23503), one-open-session-per-(register, currency)
  (23505), CDF/USD session coexistence, and handover after close.
- `scripts/verify-rls.ts` (catalog introspection) — **not yet written**, tracked in
  ROADMAP Phase 1b.
- Manual fail-closed check documented in `NEON-SETUP.md` §5 (applies once Neon is
  provisioned).
